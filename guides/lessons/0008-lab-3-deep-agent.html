By the end

Your agent writes a whole case file for a household: it plans its own to-do list, hands each scheme to a sub-agent, pauses before booking or submitting, and follows a skill you wrote.

The scenario

The same agency, a bigger job. A caseworker doesn't want one answer; they want a case file for a whole household: every scheme that might apply, the eligibility decision and the sums for each, an assessment booked where needed, and a written file at the end.

That is 15 to 25 tool calls. Lab 1's agent could try, but everything would pile up in one conversation: scheme rules, calculations, results. It has no plan to keep it on track and nowhere to put a finished document. Those are exactly the things a harness adds.

You give itA request in messages, as in Lab 1, describing the household.
It producesA to-do list (todos), files (files, including /case_file.md) and a short answer.
Calls a modelThe main agent on every step, plus one eligibility_researcher sub-agent per scheme it checks.

What is a harness?

Everything around the model that turns it into a working agent: the loop, the tools, where it keeps notes, how it manages its context, and when it stops to ask. In Lab 1 you wrote a tiny harness yourself: reason → act. Labs 3 and 4 use ready-made ones.

Lab 3 is a harness library: Deep Agents from LangChain. You build on it in Python and ship it inside your own app. Lab 4 is a harness product: Hermes Agent, a finished assistant you run and configure without code.

The idea

Same engine. create_deep_agent returns an ordinary LangGraph graph, which is why it shows up in Studio next to Labs 1 and 2. Source

One call builds the whole agent. You pass in what is specific to the agency:

create_deep_agent(
    model=get_chat_model(role="deep_agent"),
    tools=[...],                       # our citizen-services tools
    system_prompt=CASEWORKER_PROMPT,
    subagents=[ELIGIBILITY_RESEARCHER],
    skills=["/agency/skills/"],
    memory=["/agency/AGENTS.md"],
    interrupt_on={"book_appointment": True},
    middleware=[TodoListMiddleware()],  # the planning tool
)

The harness adds the rest:

Built inWhat it does here
write_todosThe agent writes and ticks off its own plan, saved in the state as todos. Added with the one middleware line above.
write_file, read_file, edit_file, ls, …A file system for notes and results. Here the files live in the thread's state, so Studio shows them; /agency/ is read from lab_3_deep_agent/agency/ on disk.
taskStarts a sub-agent with a fresh, empty context and only its own tools. Only its final reply comes back.
interrupt_onPauses before the tools you name, until a person approves or rejects.
SkillsEach SKILL.md adds only its name and one-line description to the prompt. The agent reads the full file when it needs it.
MemoryAGENTS.md is loaded into the prompt on every run: the agency's house rules.
calls a modelwaits for a personplain code

Lab 3 or Lab 4?

Both are harnesses. The difference is who owns the agent, and what you change to change it.

Lab 3 · Deep Agents (library)Lab 4 · Hermes Agent (product)
You change it byWriting Python: tools, prompts, sub-agents, approvalsSettings, connected tools, Markdown skills, and talking to it
It livesInside your app, as a graph you deployOn its own: a web dashboard, a terminal, or a chat app
Who uses itYour app's users, who never see the harnessThe person who runs it, and it learns their way of working
Agency examplesA "prepare case file" button in the caseworker portal; a nightly job that drafts appeal lettersAn officer's own assistant that answers, remembers and sends a daily summary; a developer asking for a code change

Do it

  1. Run it in Studio and watch the plan
    What you're testing. What the harness gives you for free: a plan, files and delegation you never wrote.

    With make studio running, pick the lab_3_deep_agent graph. Paste this into messages and submit:

    Prepare a case file for a household: grandparents aged 68 and 72, two working adults earning $5,500 a month together, household of 4, all citizens. One adult wants to retrain. Check every scheme that could apply and book the earliest SMG assessment if they qualify.

    Watch the state panel: todos appears first and its items tick off; files fills up. When the agent wants to book, the run pauses with an interrupt. Resume it with this value to approve:

    {"decisions": [{"type": "approve"}]}

    At the end, open files → /case_file.md in the state panel.

    Predict How many schemes will it check, and does the household qualify for SMG?

    Probably three or four: SMG for the grandparents, SUC for the adult who wants to retrain, HER for the household, maybe CSV. Per-capita income is $5,500 ÷ 4 = $1,375, under SMG's $1,500 limit, so it should book. Count the task calls: one per scheme.

    No Studio? Use the terminal instead 
    $ make deep

    Paste the same request. When it pauses, type yes. After each answer it prints the to-do list and the files. Ask Show me /case_file.md to read the file.

  2. Look inside a hand-off
    What you're testing. What a sub-agent sees, and what it costs to keep the main conversation short.

    Click one of the task tool calls. Read the description the main agent wrote for eligibility_researcher, then the reply that came back.

    Think The sub-agent starts with an empty context. What must the main agent remember to put in the description?

    Every fact the check needs: the scheme, ages, income, household size and residency. The sub-agent can't see the conversation, so a fact left out of the description is a fact it doesn't have. That is the trade: the main conversation stays short (one six-line reply per scheme instead of every rule and calculation), but each hand-off has to be complete. ELIGIBILITY_RESEARCHER's description in agent.py tells the main agent this.

  3. Close a gap: approval before submitting
    What you're testing. That an approval only exists for the tools you list, and what a person's no does.

    In the same thread, send:

    Submit the SMG application for this household.

    It submits without asking: INTERRUPT_ON in agent.py only lists book_appointment. Change it to:

    INTERRUPT_ON = {"book_appointment": True, "submit_application": True}

    Save, open a new thread, give it the household again and ask it to submit. This time it pauses. Reject it:

    {"decisions": [{"type": "reject", "message": "Not yet: the household hasn't signed the consent form."}]}
    Think Lab 2 refused to submit for an unvalidated scheme. Does Lab 3?

    No. interrupt_on asks a person every time; it doesn't know whether eligibility was checked. Lab 2's check_policy encoded the rule "validate first" in code. A harness gives you general controls (pause, permissions); the business rules are still yours to write, as a tool that refuses or as middleware.

    No Studio? Use the terminal instead

    Restart make deep after saving. When it pauses, type no: the terminal sends a reject decision.

  4. Teach it a skill
    What you're testing. How a skill differs from a prompt: it costs one line until the agent needs it.

    Open lab_3_deep_agent/agency/skills/case-file-format/SKILL.md: that is the skill the agent read before writing the case file. Now add your own. Create lab_3_deep_agent/agency/skills/appeal-letter/SKILL.md:

    ---
name: appeal-letter
description: How the agency drafts an appeal letter when a household is found not eligible. Read before writing any appeal.
---

# Appeal letter

1. Address it to "The Appeals Officer, Citizen Services Agency".
2. Quote the scheme rule that was not met, with its [source].
3. State the household's figures, including the per-capita sum.
4. Name the one new fact or document that could change the decision.
5. Keep it under 200 words. Write it to /appeal_letter.md.

    Save, open a new thread and send:

    A household of 2 earns $4,000 a month and was found not eligible for the Household Energy Rebate. Draft an appeal letter.
    Check How do you know it used your skill?

    Look for a read_file call on /agency/skills/appeal-letter/SKILL.md before write_file on /appeal_letter.md, and check the letter follows your five rules. Until that moment the model had seen only the skill's name and description. Compare agency/AGENTS.md: house rules that must apply to every case go there, because memory is always in the prompt.

    No Studio? Use the terminal instead

    Restart make deep after saving, send the request, then ask Show me /appeal_letter.md.
