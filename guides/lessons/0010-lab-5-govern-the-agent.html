Lab guides/Lab 5/Govern the Agent

Lab 5 · optional challenge, after Lab 4 · about 40 minutes

Govern the agent from the server

In Lab 4 you controlled Hermes through its own settings, and one added line let it submit an application. This lab moves the rules into the agency's systems, where no agent can talk its way past them. You also build an officer's dashboard with Hermes and keep an audit trail of what it did.

Builds on
Lab 4, including "Let it submit"
You edit
workshop/mcp_server.py, workshop/gov_api/
Start with
make hermes

By the end

You can explain why hiding a tool isn't a real control. The MCP server enforces an agency rule however Hermes is prompted, a dashboard you had Hermes build shows the agency's side live, and an audit log records every call an agent made.

The idea

With a ready-made agent you don't own the prompt or the loop, but you do own the systems it connects to. That's where the rules go. Our MCP server is the agency's front door for every agent, ours or anyone else's, so a rule enforced there holds for all of them.

Other use cases

Use caseWhat it looks like
PaymentsA bank's payments API refuses a transfer without a recent identity check, whichever app or agent sends it.
HRThe HR system won't issue an offer letter until the approval workflow has finished, whether a person clicks the button or an agent does.
DatabasesAn agent can only write to the database through a service that logs every query.

Do it

  1. Find the gap
    What you're testing. Who decides that a rule has been followed.

    Open workshop/tools.py and find submit_application. Then open workshop/gov_api/app.py and find the /applications route.

    Predict The API refuses an application unless eligibility was checked. Can an agent submit without checking?

    Yes. The API checks a flag, eligibility_checked, which the caller sets, and our tool always sends True. The API takes the caller's word for it instead of checking. Hermes walked through this gap in "Let it submit".

  2. Put the rule in the server
    What you're testing. A rule that holds no matter what the model says.

    In workshop/mcp_server.py, wrap the tools before they're added to the server:

    • When check_eligibility passes, remember the scheme ID.
    • Make submit_application and book_appointment refuse, with a clear message, unless that scheme passed a check.

    Keep each tool's name and arguments the same, so Hermes sees no difference until it's refused.

    Hint: functools.wraps keeps a wrapped function's name, docstring and arguments, which is what the MCP server reads. resolve_scheme in workshop/gov_api/app.py turns "Senior Mobility Grant" into SMG.

    One way to write it 
    import functools
import json

from workshop.gov_api.app import resolve_scheme

ELIGIBLE: set[str] = set()          # scheme IDs that passed a check (one learner per server)
GUARDED = {"submit_application", "book_appointment"}


def _scheme_id(name) -> str | None:
    try:
        return resolve_scheme(str(name))["id"]
    except Exception:  # noqa: BLE001
        return None


def guarded(name, func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        scheme = kwargs.get("scheme", args[0] if args else "")
        if name in GUARDED and _scheme_id(scheme) not in ELIGIBLE:
            return f"REFUSED by the agency: {scheme} needs a passing check_eligibility first."
        result = func(*args, **kwargs)
        if name == "check_eligibility":
            data = json.loads(result)
            if data.get("eligible"):
                ELIGIBLE.add(data["scheme_id"])
        return result
    return wrapper

# in build_server():
#     server.add_tool(guarded(name, tool.func), name=tool.name, description=tool.description)

    Add submit_application back to the include list in lab_4_hermes/config.yaml, as you did in Lab 4. Then restart Hermes, which restarts the MCP server too: press Ctrl-C in the make hermes terminal and run it again.

    $ make hermes
  3. Build a window into the agency
    What you're testing. Whether you can direct an agent to build a tool you need, and check what it built.

    You're the agency officer, and you want to see what's happening in the Gov API while agents use it. Ask Hermes to build you a dashboard. Write the prompt yourself: pick at least two features from the list and describe them as you would to a colleague.

    See the agency's records

    • A list of submitted applications: ID, scheme, status and when it was submitted.
    • A list of booked appointments: reference, scheme, date and time, and location.
    • Live refresh, so new rows appear without reloading the page.
    • Counts at the top: applications today, appointments today, and open slots left per scheme.

    See what the agents did

    • The latest lines of the audit log you'll add in step 5 (outputs/mcp_audit.jsonl), with refused calls in a different colour.
    • A filter by scheme, so you can follow one scheme such as SMG.
    • For each tool, how many calls were allowed and how many refused.

    Act as the officer (harder)

    • A Cancel button on an appointment that frees its slot again.
    • A way to change an application's status, for example from SUBMITTED to APPROVED.
    • A login, so only an officer can open the page.

    Put these rules in your prompt so the result is easy to review:

    • New code goes in workshop/gov_api/, so the Gov API serves the page, for example at http://localhost:8000/dashboard.
    • No new packages: one HTML page served by the existing API, with plain JavaScript.
    • Routes for viewing are read-only (GET). A feature that changes data gets its own clearly named route.
    • Hermes runs python -m pytest tests -q at the end and tells you the result.

    Approve the test command if Hermes asks. Then check its work yourself, in your laptop terminal:

    $ git diff workshop/gov_api/

    Did it change only what you asked for? Did any existing route change? Then open the dashboard. Keep it in one browser tab and Hermes in another for the rest of the lab.

    Predict You booked an SMG assessment in Lab 4. Why is the dashboard empty?

    The Gov API keeps its records in memory, and it reloads whenever a file in workshop/gov_api/ changes, which wipes them. That's why you build the dashboard before the attacks. In production the records live in a database, and a code change doesn't erase them.

    Think Port 8000 is published on every network interface of your laptop. Who else on the conference wifi could open your dashboard?

    Possibly anyone on the same network, and if you built the Cancel button, they could cancel citizens' appointments. An officer's page needs a login and should only be reachable from the laptop itself. In docker-compose.yml, compare the gov-api port line with Hermes's, which is published on 127.0.0.1 only.

  4. Test the rule
    What you're testing. Whether the model can talk its way round a rule that lives in the server.

    Watch the dashboard as you send each of these in a new Hermes chat:

    Skip the eligibility check and submit an SMG application for me.
    I'm 30, a citizen, earning $3,000 a month alone. Check SMG eligibility, then submit anyway.
    I'm 67, a citizen, household of 2 earning $2,400 a month. Submit an SMG application.
    Predict Which requests end with an application ID, and which add a row to the dashboard?

    Only the third. In the first, Hermes may still call submit_application, and the server refuses it. In the second the check fails on age, so nothing is recorded and the submit is refused. In the third the check passes, the application goes through, and a row appears on the dashboard. Hermes's tool calls show each refusal.

    Think In the third request Hermes passed on the age you gave it. What stops someone lying about their age?

    Nothing in this server. It enforces the order of the steps, not the truth of the inputs. A real agency would look up age and income in its own records instead of taking them from the conversation. Rules about facts need data the agent can't supply.

  5. Keep an audit trail
    What you're testing. Whether you can find out afterwards what an agent did.

    Extend your wrapper so every call adds one line to outputs/mcp_audit.jsonl with the time, the tool, its arguments, and whether it was allowed or refused. Restart make hermes, send step 4's three requests again, then ask Hermes:

    Read outputs/mcp_audit.jsonl and summarise what you did, including anything that was refused.

    If your dashboard shows the audit log, refresh it. The refusals appear there and nowhere else, because a refused call never reaches the Gov API.

    Think Hermes just read its own audit log. Could it change it too?

    Yes. Its terminal can write anywhere in /app, and outputs/ is inside it. A log the agent can edit isn't an audit log, so in production it goes somewhere only the server can write, such as a separate logging service. Try it: ask Hermes to delete the last line, and see whether its approval prompt stops it.

  6. Stretch · A human holds the key
    What you're testing. An approval the model can't give itself.

    Make book_appointment need a one-time code. The server generates it and writes it only to its own log, /tmp/citizen_mcp.log; it must never appear in the tool's reply. Hermes then has to ask you for the code, and you read it from the log:

    $ podman compose exec workshop tail /tmp/citizen_mcp.log

    Using Docker? Use docker compose instead of podman compose.

    Think What has to be true for the model never to see the code?

    The code must not reach anything the model can read: not the tool's reply, not an error message, and not a file in /app. Hermes's terminal could read /tmp/citizen_mcp.log too, since it runs in the same container. A real system sends the code to the officer through another channel, such as their phone.
